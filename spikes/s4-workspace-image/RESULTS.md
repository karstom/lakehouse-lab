# S-4 Results: `lakehouse-workspace` image

**Verdict: PASS on all four criteria, with one policy question left for the lead** (see
"Repair round" below). `./test.sh` exits 0. It passed on two consecutive runs against a freshly
recreated container, and again after the repair-round changes (2026-09-25, server $LAB_SERVER).
ADRs covered: ADR-007, ADR-008, ADR-012. Open question covered: OQ-2.

## OQ-2: Spark Connect vs classic driver (measured)

Both runs did the same work: `range(5M) -> groupBy(k).sum -> collect`, then `createDataFrame -> toPandas`.

| | Spark Connect client (`pyspark-client`) | Classic in-container driver (`pyspark` + JRE 17) |
|---|---|---|
| Added to the image | pyspark-client wheel is about 2 MB, plus grpc/pandas/pyarrow that the image needs anyway | **+722 MB** (image 2.83 GB instead of 2.11 GB): 455 MB wheel of Spark jars plus the JRE |
| Workspace memory | about 135–225 MiB for the whole workspace container after the job | **466 MB RSS for the driver JVM alone**, per user, on top of JupyterLab |
| Session start | 1.0 s (gRPC connect) | 7.0 s (JVM start) |
| 5M-row groupBy | 0.9–1.2 s warm (5.4 s on the first job, while the server JVM warms up) | 5.2 s |
| Isolation | Each user gets their own `session_id`, and temp views are per session (verified: a view made in session A is not visible in B). They **share** one server JVM, its memory, its SparkContext and its Spark UI. | A full JVM per user, fully isolated, and the user's own Spark UI on :4040 in their container |
| Version coupling | The client must match the server's Spark minor (4.1.3 ↔ 4.1.3 here). The server holds the Iceberg jars and the catalog config, so users can't change them. | pyspark in the workspace **is** the driver. Jars and config live in the workspace (the V2 `REG_ICEBERG_JAR_VERSIONS` class). |
| Gaps | No RDD API and no `sparkContext` (Connect limitation). The Spark UI belongs to the server, not the user. **Spark Connect has no built-in end-user auth**, so a shared server needs a proxy or token in front of it (Phase 1). | Heavy image and per-user memory |

**Recommendation:** make Spark Connect the default and keep `pyspark-client` in the image, which confirms the current lean in OQ-2. For RDD and Spark UI lessons, run a classic driver from a separate opt-in image or profile (the `workspace-classic` stage shows it works: +722 MB). Don't put it in every workspace. Phase 1 must decide two things. First, whether it runs one shared Connect server, which only isolates at session level, or one server per user or group. Second, how Connect is authenticated: Keycloak token through a gRPC proxy, or a per-user server.

## Surprises

1. **jupyter-ai 3.x is a metapackage.** The `jupyter_ai` package is empty, and "enabled" means its component
   extensions are. Also, **no persona works out of the box.** The 8 registered personas (`claude-acp`, `codex-acp`,
   `goose-acp`, …) are ACP clients that need the matching agent CLI installed. The built-in `jupyternaut` persona
   comes only with the `jupyter-ai[jupyternaut]` extra, which pulls in litellm. The chat UI loads but has nobody to
   talk to until Phase 5 (ADR-014) picks an agent or extra.
2. **jupyter-ai starts an MCP server inside every workspace** (`jupyter_server_mcp`, `localhost:3001`, notebook
   tools). It also writes a runtime file, so `jupyter server list` shows a second "server" whose entries have
   no `token`. test.sh therefore selects the server by port 8888. That MCP server is useful for ADR-014, but a
   default that listens on a port should be a deliberate decision.
3. **DuckDB has no environment variable for its extension directory** (checked the 1.5.5 binary and
   `duckdb_settings()`). It looks in `~/.duckdb/extensions`, and JupyterHub mounts `$HOME` over that. The fix is to
   install into `/opt/duckdb/extensions` at build time, and have the entrypoint symlink
   `~/.duckdb/extensions/v<ver>` to it. This also survives image upgrades, because a new DuckDB version gets a new
   link. The repair round moved the script from `CMD` to `ENTRYPOINT`, so a spawner that overrides `cmd` still gets
   the link (tested). Only an `entrypoint` override bypasses it. DockerSpawner does not override that by default,
   but the Phase 1 hub config must not override it either.
4. **dbt-core 1.12 is heavy:** it pulls in `metricflow`, `dbt-core-experimental-parser` (55 MB wheel), `posthog`
   and `snowplow`. The image sets `DBT_SEND_ANONYMOUS_USAGE_STATS=false` and `DO_NOT_TRACK=1` so dbt doesn't try to
   phone home.
5. **The resolver picked pandas 3.0.6, pyarrow 25 and numpy 2.5.** Connect `toPandas()`, PyIceberg and DuckDB all
   worked with them. JupySQL wasn't tested against a live database (that's Phase 1).
6. **code-server is 34% of the image** (712 MB). It is still well under budget.
7. Operational: ssh sessions to the server that print nothing for a few minutes hang forever, probably because
   WSL2 NAT drops idle connections. Run long commands with `ssh -o ServerAliveInterval=15`. This is not a problem in
   the spike itself.

## Implications for the ADRs

- **ADR-012:** "Versions only in versions.env" holds for everything you choose (the Dockerfile and
  `requirements.in` use `${VAR}` only). Reproducibility needs a **generated transitive lockfile**, though
  (`lock/constraints.txt`, 226 pins). The CI version-literal check must exempt generated lockfiles, and CI
  should regenerate the lock (`build.sh --relock`) whenever `versions.env` changes. Add `PYTHON_IMAGE_TAG`,
  `JUPYSQL_VERSION` and `JUPYTERLAB_GIT_VERSION` to `versions.env`, plus `PYTHON_IMAGE_DIGEST`, since
  base images should be pinned by tag **and** digest. Phase 1 could apply that rule to every third-party image.
- **ADR-007:** Confirmed. One image (2.11 GB) serves both JupyterHub (`jupyterhub-singleuser` 5.5.2) and
  standalone use, and code-server via jupyter-server-proxy works with `--auth=none` behind Jupyter's own auth.
  Phase 1 still has to test an actual DockerSpawner spawn, which is covered by S-3/Phase 1, not here.
- **ADR-008:** Confirmed. dbt-core 1.12.5 and dbt-trino 1.10.5 coexist with the rest of the stack with no
  conflicts.
- **ADR-014 / OQ-7/8:** jupyter-ai 3.2 ships with no usable persona. Choose between the `[jupyternaut]` extra
  (litellm, which fits the gateway plan) and an ACP agent CLI baked into the image. Also decide whether the
  in-workspace MCP server stays on.
- **OQ-2:** Resolved in favour of **Spark Connect by default**, with the classic driver as an opt-in variant.
  Connect authentication and server-per-user vs shared server become Phase 1 design items.

## Repair round (2026-09-25)

The verifier found everything working. Its one finding is a policy question.

- **(A) `lock/constraints.txt` vs rule 5 / ADR-012: needs a lead decision, no builder change.** The file holds 226
  literal transitive pins (for example `agate==1.9.1`) outside `versions*.env`. It is generated by
  `build.sh --relock` from a `pip freeze` of the image, and it drops the top-level packages, whose pins stay in
  `versions*.env`. Deleting it would let transitive packages float, which breaks criterion 1 (reproducible build),
  so the builder recommends keeping it. **Proposed ADR-012 wording:** "Generated lockfiles (header `# GENERATED by
  … Do not edit`, e.g. `lock/constraints.txt`) are exempt from the version-literal check. CI re-runs
  `build.sh --relock` when `versions.env` changes and fails if the committed lock differs." If the lead rules
  otherwise, the fallback is to remove the `-c lock/constraints.txt` from the Dockerfile and accept floating
  transitive packages.
- **(B) Done.** `start-workspace.sh` is now the `ENTRYPOINT` (`["tini","-g","--","/usr/local/bin/start-workspace.sh"]`,
  `CMD []`). Programs named in the CMD are `exec`'d after the wiring runs. With an empty CMD, or with flags only, it
  selects `jupyterhub-singleuser` or `jupyter lab` as before. `test.sh` has new checks. The running container shows
  PID 1 is `tini -g -- /usr/local/bin/start-workspace.sh` and its child is `jupyter-lab`.
- **(C) Done.** The base is now `python:${PYTHON_IMAGE_TAG}@${PYTHON_IMAGE_DIGEST}` (the digest is in
  `versions.local.env`). That fixes the apt packages (bookworm snapshot in the base), python and
  pip/setuptools/wheel by content hash. What remains unpinned by hash: the `apt-get install` step resolves against
  the live bookworm mirror, so a Debian point release can change `curl`/`git`/`tini` builds. The code-server
  tarball and the DuckDB extension binaries are fixed by version and URL, but not verified against a sha256.
  Phase 1 could add sha256 checks in `install-code-server.sh` and `install-duckdb-extensions.py`, and use
  `snapshot.debian.org` or accept apt drift.

Image after the repair: `2106443498` bytes = 2.11 GB. It was rebuilt from cache, because the digest resolves to the same base
the tag already pointed to.
